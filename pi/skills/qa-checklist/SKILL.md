# qa-checklist

把本次代码改动转成一份**作者本人照着勾的自测清单**。读者是写这段代码的人，不是外部测试人员——所以不写背景、不写环境说明、不写交付文档的头尾，只给能立刻动手执行的测试项。

## 输出位置与命名

- **目录**：当前工作目录下的 `./.qa/`（不存在则创建）
- **文件名**：`<主题>.md`，主题用小写短横线连接，具体到能一眼看出测的是哪次改动
  - 好：`calibration-card-dispatch.md`、`patrol-stall-timeout.md`、`login-token-refresh.md`
  - 差：`qa.md`、`test.md`、`checklist.md`、`changes.md`
- **冲突处理**：目标文件已存在时追加时间戳后缀 `<主题>-YYYYMMDD-HHMM.md`，**绝不覆盖**（同一功能常测多轮，旧的勾选记录要留着）

写入前先探测：`ls ./.qa/ 2>/dev/null`。

## 文档结构（唯一模板，不得增删段落）

````markdown
# <改动主题> QA Checklist

## 1. <功能点名称>

- [ ] <条件/操作>，<可观察的预期结果>
- [ ] <条件/操作>，<可观察的预期结果>

## 2. <功能点名称>

- [ ] <条件/操作>，<可观察的预期结果>
````

**除上述三层外，禁止输出任何其他内容**：不要元信息表（版本/commit/日期）、不要「测试前准备」、不要功能点级的「触发方式」行、不要「改动说明」、不要「回归范围」、不要「问题记录」、不要「测试结论」、不要文末总结。触发方式直接内联进测试项句子里。

## 功能点划分

- 按**可感知的行为单元**划分：一个功能点 = 一个入口 + 一类行为
- 用**业务语言**命名：「校准点卡号下发」「定点巡检停滞超时判定」「登录态过期后自动续签」
- **禁止**按代码结构划分（`chargingPoint.cpp 的 syncCalibration`、`useAuth hook`）——那会诱导出无法手动验证的测试项
- **禁止**把一个需求单/缺陷单整体当成一个功能点——一个单里往往含多个独立行为，拆开
- 测试项条数不设限，该多则多

## 测试项硬规则

1. **可手动执行、可判定通过/失败**。写不出观察方式的不许进清单——「函数返回值正确」「内存无泄漏」「代码健壮性提升」一律删掉，除非能给出具体观察点。
2. **一项只断言一件事**。多个断言拆成多条，方便勾选时定位到底哪条挂了。
3. **预期必须具体**。写「机器人侧读到 `0xCC0003F3`，不为 0」，不写「显示正常」「功能可用」「符合预期」。
4. **用真实可用的值**。具体卡号、具体 URL、具体账号、具体 SQL，不写 `<某个值>`、`xxx`、`测试数据 A` 这类占位符。
5. **允许依赖日志/数据库/接口返回作为观察点，但必须写清去哪看**：日志路径与关键行、表名与字段、接口路径与响应字段。
6. **只测本次改动涉及的行为**，不铺开测无关功能。

### 正反例

| 反例 | 问题 | 改成 |
| --- | --- | --- |
| `- [ ] 校准点同步功能正常` | 无法判定 | `- [ ] 用卡号 cc0003f3 新增校准点并保存，机器人侧读到 0xCC0003F3，不为 0` |
| `- [ ] 卡号解析改为无符号，边界值均正确` | 多个断言糊在一起 | 拆成 `7fffffff` / `80000000` / `ffffffff` 三条 |
| `- [ ] 输入非法卡号时有告警` | 没说去哪看 | `- [ ] 卡号填 zzzz 保存，Log/BWRobotServer.log 出现 Skip calibration point 告警，该条不下发` |
| `- [ ] 调用接口返回成功` | 值不具体 | `- [ ] POST /api/charging-point 返回 200 且 body.code=0，tbl_robot_charging_point 新增一行 firstCard='cc0003f3'` |
| `- [ ] syncCalibration() 被正确调用` | 按代码结构写，手测不了 | 换成该调用对外产生的可观察结果 |

## 生成流程

1. **确定改动面**，按以下优先级：
   - 用户显式指定范围（commit 区间、分支、文件列表）→ 以其为准
   - 当前会话上下文中已有本次改动 → 直接用
   - 上下文不足 → 自查 git：`git status --short`（未提交改动）、`git diff`、`git show --stat HEAD`（最近一次提交）
2. **拿不准就问，不许猜着写**。diff 里混着多组不相关改动、或无法判断用户想测哪一部分时，先问清楚再动手。
3. **读关键代码确认真实行为**。预期结果必须来自代码的实际实现（边界怎么算、失败走哪个分支、日志打的什么词），不能凭改动标题想象。
4. **提炼功能点**，按行为单元归组。
5. **逐个功能点写测试项**，主动覆盖正常路径、边界值、失败/异常路径——只写了正常路径的清单不合格。
6. **探测文件冲突** → 用 write 一次性写入完整文档。
7. **回执**：告知绝对路径 + 一句话概括（几个功能点、共几项）。

## 反例（整份文档层面）

- 输出里带了「测试环境」「前置条件」「被测版本」段落——违反模板，删掉
- 功能点叫「第一部分：后端改动」「第二部分：前端改动」——按代码层分组，不是行为单元
- 全篇只有正常路径，没有一条边界或失败场景
- 测试项写成「步骤 1/2/3 + 预期结果」的多行块——必须压成一行一个 checkbox
- 直接把内容贴在对话里不落盘，或落盘后不给路径
