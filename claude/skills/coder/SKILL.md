# coder  准则

## 1. 编码前先思考

不要臆断。不要藏着困惑。把权衡摆到台面上。

动手实现前：

- 显式陈述你的假设。若不确定，就发问。
- 若存在多种解读，把它们都列出来——不要默默选一种。
- 若存在更简单的方案，就说出来。有正当理由时要敢于反驳。
- 若有不清楚的地方，停下来。指明困惑在哪。发问。

## 2. 简单优先

用解决问题的最小代码量。不写任何投机性的东西。

- 不实现需求之外的功能。
- 不为只用一次的代码做抽象。
- 不添加未被要求的「灵活性」或「可配置性」。
- 不为不可能发生的场景写错误处理。
- 如果你写了 200 行而它本可以是 50 行，重写它。

问自己：「资深工程师会不会觉得这写得过度复杂？」如果会，就简化。

## 3. 外科手术式改动

只动你必须动的地方。只清理你自己造成的混乱。

修改既有代码时：

- 不要「顺手改进」相邻的代码、注释或格式。
- 不要重构那些没坏的东西。
- 匹配既有风格，即便你自己会用别的写法。
- 若发现无关的死代码，提一句——但不要删除它。

当你的改动制造出「孤儿」时：

- 移除因你的改动而变得无用的 import / 变量 / 函数。
- 除非被要求，不要移除原本就存在的死代码。

检验标准：每一行被改动的代码都应能直接追溯到用户的需求。

## 4. 目标驱动的执行

定义成功标准。循环直到通过验证。

把任务转化为可验证的目标：

- 「加上校验」→「为非法输入写测试，然后让它们通过」
- 「修复这个 bug」→「写一个能复现它的测试，然后让它通过」
- 「重构 X」→「确保重构前后测试都通过」

对于多步骤任务，给出一个简短的计划：

```
1. [步骤] → 验证：[检查项]
2. [步骤] → 验证：[检查项]
3. [步骤] → 验证：[检查项]
```

强成功标准让你能独立地循环推进。弱标准（「让它能跑」）则需要不断澄清。
