# coder

编码时应遵循的规范。本文件给出**所有语言通用**的规范与优雅准则；具体语言的规则见
下方[分语言规则](#分语言规则)索引。

## 通用规范（所有语言）

### 命名

- 变量命名：变量名应具有描述性，能清楚表明其用途，避免无意义的 `a`/`tmp`/`data`。
- 函数命名：函数名应使用动词或动词短语，描述函数的行为（如 `parseConfig`）。
- 类命名：类名应为名词且具有描述性，遵循所在语言的命名约定。
- 自解释优先：用清晰的命名减少对注释的依赖，让代码本身表达意图。

### 注释

- 注释应简洁明了，解释代码的**意图**或复杂逻辑，而非复述代码「做了什么」。
- 优先解释「为什么这样做」，而非「这行在做什么」。
- 删除注释掉的死代码与临时调试输出，不要把它们留在提交里。

### 复用与设计

- 避免重复代码（DRY）：将重复的逻辑提取到函数或类中，提高可维护性。
- 单一职责：每个函数或类应只承担单一职责。
- 善用设计模式解决结构性问题，但不过度设计（YAGNI），简单问题用简单方案。

## 优雅准则（让代码读起来更优雅）

以下为可逐条对照的具体准则，编码时应主动检查：

- **函数短小**：一个函数只做一件事，理想控制在 ~30 行内；过长则按职责拆分。
- **提前返回**：用 guard clause / 提前返回替代深层嵌套，嵌套层级尽量 ≤ 3 层。
- **消除魔法值**：不出现裸的魔法数字 / 魔法字符串，提取为有名常量或枚举。
- **拆解复杂表达式**：把复杂条件或表达式拆成有名的中间变量，让逻辑可读。
- **一行一事**：一行只表达一件事，控制行宽，避免把多步操作挤在一行。
- **保持对称与一致**：相似的逻辑用相似的写法、命名和顺序，降低阅读负担。
- **显式错误处理**：错误 / 异常要显式处理，不吞异常、不忽略返回的错误。
- **优先复用既有能力**：优先使用语言特性与标准库，不重复造轮子。
- **可读优先于炫技**：避免「聪明」但晦涩的写法，清晰永远优先于取巧。
- **就近声明**：变量在靠近第一次使用处声明，缩小作用域。
