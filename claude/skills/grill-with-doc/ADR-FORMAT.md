# ADR 格式

ADR 存放在 `docs/adr/` 目录中，采用顺序编号：`0001-slug.md`、`0002-slug.md`，依此类推。

惰性创建 `docs/adr/` 目录 —— 仅在需要第一个 ADR 时创建。

## 模板

```md
# {决策的简短标题}

{1-3 句话：背景是什么、我们决定了什么、为什么。}
```

就这么简单。一个 ADR 可以只有一段话。其价值在于记录"曾做出过某个决策"以及"为什么" —— 而不在于填满各个小节。

## 可选小节

仅在能带来真正价值时才收录这些小节。大多数 ADR 都不需要它们。

- **Status（状态）** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）—— 当决策会被重新审视时很有用
- **Considered Options（已考虑的选项）** —— 仅当被否决的备选方案值得记住时
- **Consequences（后果）** —— 仅当需要点明不显而易见的下游影响时

## 编号

扫描 `docs/adr/`，找到现有的最大编号，加一。

## 何时应当提议写一个 ADR

以下三点必须同时成立：

1. **难以逆转** —— 日后改变主意的代价不容忽视
2. **缺乏背景就会令人费解** —— 未来的读者看到代码会纳闷"他们到底为什么要这么做？"
3. **是真实权衡的结果** —— 确实存在多个备选方案，而你出于具体原因选择了其中之一

如果一个决策很容易逆转，就跳过它 —— 反正你会去逆转它。如果它并不令人费解，就没人会纳闷为什么。如果根本不存在真正的备选方案，那么除了"我们做了显而易见的事"之外没什么可记录的。

### 哪些情况符合条件

- **架构形态。** "我们使用 monorepo。""写模型采用事件溯源，读模型投影到 Postgres。"
- **上下文之间的集成模式。** "Ordering 和 Billing 通过领域事件通信，而非同步 HTTP。"
- **带来锁定效应的技术选型。** 数据库、消息总线、认证提供方、部署目标。不是每个库都算 —— 只算那些要花一个季度才能替换掉的。
- **边界与范围决策。** "客户数据由 Customer 上下文拥有；其他上下文只通过 ID 引用它。" 明确的"不做什么"和"做什么"同样有价值。
- **对显而易见路径的刻意偏离。** "我们使用手写 SQL 而非 ORM，因为 X。" 任何会让理性读者以为应该反过来做的情况。这些记录能阻止下一位工程师去"修复"一个本是刻意为之的设计。
- **代码中不可见的约束。** "由于合规要求，我们不能使用 AWS。""由于合作方 API 合同的约定，响应时间必须低于 200ms。"
- **被否决的备选方案，当否决理由不显而易见时。** 如果你考虑过 GraphQL，却因某些微妙原因选了 REST，就记录下来 —— 否则半年后又会有人重新提议用 GraphQL。
