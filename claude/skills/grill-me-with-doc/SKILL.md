<what-to-do>

针对这份计划的每一个方面对我进行不间断的盘问，直到我们达成共识。沿着设计树的每一条分支逐一深入，逐个解决各决策之间的依赖关系。对于每个问题，都给出你推荐的答案。

每次只问一个问题，在得到该问题的反馈之前不要继续下一个。

如果某个问题可以通过探索代码库来回答，那就去探索代码库，而不是发问。

## 领域意识

在探索代码库时，同时留意是否存在既有文档：

### 文件结构

大多数仓库只有单一上下文（context）：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录下存在 `CONTEXT-MAP.md`，说明该仓库有多个上下文。这张映射表会指明每个上下文所在的位置：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文专属决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

按需惰性创建文件——只有当你有内容要写时才创建。如果不存在 `CONTEXT.md`，在第一个术语被厘清时再创建它。如果不存在 `docs/adr/`，在第一份 ADR 有必要写时再创建它。

## 会话进行中

### 对照术语表进行挑战

当用户使用的术语与 `CONTEXT.md` 中既有的语言相冲突时，立即指出来。“你的术语表把‘cancellation’定义为 X，但你这里似乎指的是 Y——到底是哪一个？”

### 打磨含糊的措辞

当用户使用模糊或含义过载的术语时，提出一个精确的规范术语。“你说的是‘account’——你指的是 Customer 还是 User？这两者是不同的东西。”

### 讨论具体场景

在讨论领域关系时，用具体场景对其进行压力测试。设计能够探查边界情形的场景，迫使用户对各概念之间的边界给出精确说法。

### 与代码交叉验证

当用户陈述某个机制是如何运作的时候，检查代码是否与之一致。如果发现矛盾，把它摆出来：“你的代码取消的是整个 Order，但你刚才说可以做部分取消——到底哪个是对的？”

### 就地更新 CONTEXT.md

当一个术语被厘清时，当场更新 `CONTEXT.md`。不要把这些攒到一起批量处理——在它们发生时就记录下来。使用 [CONTEXT-FORMAT.md](./CONTEXT-FORMAT.md) 中的格式。

`CONTEXT.md` 应当完全不含任何实现细节。不要把 `CONTEXT.md` 当作规格说明书、草稿纸或存放实现决策的仓库。它只是一份术语表，仅此而已。

### 谨慎地提议创建 ADR

只有当以下三点同时成立时，才提议创建一份 ADR：

1. **难以撤销**——日后改变主意的代价是实实在在的
2. **缺乏背景便令人费解**——未来的读者会纳闷“他们当初为什么要这么做？”
3. **是一次真实权衡的结果**——确实存在其他可选方案，而你出于具体理由选择了其中之一

只要这三点缺了任意一点，就跳过 ADR。使用 [ADR-FORMAT.md](./ADR-FORMAT.md) 中的格式。
